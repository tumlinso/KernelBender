## Design briefs produced

### B1 — Synchronous threshold update over 64-vertex graphs

**Decision: probe a fused packed-state path against direct CSR.** For each
output vertex `v`, keep the existing CSR incoming-neighbor list and accumulate
`c_v = Σ_(u in In(v)) ((x_old >> u) & 1)` until either `c_v >= 2` or
`c_v + remaining_degree < 2`. The result bit is `r_v = [c_v >= 2]`. Threads
own fixed vertex positions; each warp evaluates 32 positions and ballots the
32 predicates to form one half of the 64-bit output. Have one lane per warp
write its mask to a two-word shared slot, then use one CTA barrier before a
thread combines both halves into the 64-bit result. All threads must reach the
ballot with the named full-warp mask and the CTA barrier with matching
participation. All reads use the old input word and the output is separate, so
the transition is synchronous. This composes threshold-only
demand, positional identity, bounded early termination, and direct packed
output without a scalar state array.

The strongest control is a straightforward CSR count-and-threshold kernel
that processes every edge, with the same warp ballot for packed output. The
early-exit path is exact because the remaining contribution is bounded by the
number of unvisited edges. It is only a performance hypothesis: sparse active
states, high-degree rows, hostile edge order, and warp divergence can erase the
saved loads. First compare full-path edge visits and runtime over active
density, degree, and edge ordering, including empty and degree-63 rows. Preserve
all-zero/all-one state and the vertex-63 case.

KernelWiki's `hw-volta-integer-routing` and `hw-volta-participation` require
named lanes to participate in the same synchronized ballot; a mask does not
make absent/inactive sources valid. This design has two
full 32-lane warps for exactly 64 vertices; any tail/generalized shape must
derive its mask from actual participants. Keep CTA synchronization out of the
warp-local ballot path. The local CPU oracle also checks a graph where an
in-place update differs from the specified synchronous update.

### B2 — Repeated sparse weighted threshold

**Decision: probe an exact monotone screen, retaining sparse multiply as the
control.** For each fixed row, sort its 32 positive-weight edges once by
descending weight and precompute suffix upper bounds
`U_k = Σ_(j≥k) w_j`. For query bit-vector `q`, visit edges in that order with
partial sum `p_k = Σ_(j<k) w_j q[col_j]`. Emit one as soon as `p_k >= tau_i`;
emit zero as soon as `p_k + U_k < tau_i`; otherwise finish the row and compare
the exact sum. Because `q` is binary and every weight is nonnegative, these
bounds are sound for every allowed input; this is not approximate screening.
The consumer receives only the threshold bit, so no weighted intermediate is
stored.

Compare with sparse matrix multiplication for 64 right-hand sides followed by
thresholding. Charge the one-time sorting/bound construction and extra bound
storage to `P`, then compare `P + 512*C_screen` with `512*C_sparse`; include
all 64×4096 output bits, launches, query reads and invalidation if A/tau
changes. There is no established reuse break-even from the fixture alone.
Thresholds at 1 may resolve quickly; all-zero queries and thresholds near the
row maximum can traverse every edge. The falsifier is an exact CPU comparison
followed by an edge-visit and full-kernel sweep over realistic query/threshold
distributions, plus worst-case all-zero/all-one inputs and reuse counts 1 and
512. Do not infer that E11's packed AND+POPC result applies: that result covered
a different dense 16×16 output and only one measured iteration.

This is a new combination of fixed preparation, demanded-predicate output,
and exact suffix bounds. The short oracle tests cover exact-threshold and
above-maximum outcomes, but do not test a GPU implementation or certify any
workload distribution.

### B3 — Four-by-four bilinear operator and retained ownership

**Decision: retain a batched small-GEMM/SIMT baseline and probe explicit PTX
only if the complete ownership route is cheap.** The semantic equation is
`C_s = A_s B_s`, using FP16 inputs, FP32 accumulation and one FP16 output
rounding. The next stage can apply its elementwise function in the supplied
lane/slot map. A concrete experimental route packs four independent 4×4
products into the four independent `m8n8k4` products by zero-padding each
4×4 problem inside an 8×8 form. That pays padded work and must use the exact
explicit PTX coordinate map, then route each needed result into the consumer's
fixed owner `(lane=(4*j+i+16*(s mod 2)) mod 32, slot=floor(s/2))`. Keep
results distributed through the elementwise stage; do not round-trip through
row-major memory unless the comparison shows it helps.

For SM70 the Wiki records `mma.sync.aligned.m8n8k4.row.col.f32.f16.f16.f32`
as a full-warp collective that computes four independent 8×8×4 products.
All 32 lanes must execute compatibly; the per-product lane groups do not
authorize a partial-warp branch. The exact PTX fragment map is available, but
it is a different contract from opaque WMMA raw storage. E09 validated the
explicit map for that instruction form and did not establish WMMA ownership or
application-level speed. Here the four-by-four padding and required map
composition remain unimplemented; under the corrected group-local sample
contract, the printed owner map assigns four samples to 64 unique lane/slot
pairs per warp (tested by CPU oracle), but matching it to PTX accumulator
slots still needs a labeled-coordinate implementation test.

Compare the full custom producer → ownership routing → consumer path against a
batched cuBLAS route and a fused SIMT route. Test one-hot/labeled coordinates,
all quadrants, finite-precision output, register pressure, and any shuffle or
shared exchange. V100 numerical documentation says input conversion,
accumulation and output conversion are separate; the finite `0.02` fixture
tolerance must be checked against FP64 for the actual FP16 inputs. No measured
Tensor Core advantage is implied.

### B4 — Large ordinary dense GEMM

**Decision: conventional.** Use the eligible cuBLAS/cuBLASLt dense FP16 GEMM
path as the baseline for the contiguous 8192×4096 by 4096×8192 operation.
There is one use, the complete result is observable, and the task gives no
fixed operand, sparse structure, fused projection, unusual numerical
requirement, or ownership opportunity. A custom circuit currently removes no
known caller-visible work. Revisit only if measurement or a changed consumer
reveals such a structure. This is a negative result about this fixture's
design choice, not a speed comparison; no GPU timing ran.

### B5 — Asynchronous global-to-shared mechanism requested on V100

**Decision: block the requested native mechanism on SM70 and offer a public
fallback.** `cp.async` and hardware-accelerated split barriers are SM80
features. The SM70 feature page explicitly excludes `cp.async`; finding an API
named `memcpy_async` does not establish native overlap, since earlier targets
may take a software/API fallback. The Ampere page says the copy's completion,
consumer completion, buffer reuse and barriers are separate obligations.

On V100, compare a simple public global-load/register/store-to-shared path with
a software-managed double buffer and explicit supported barriers only if the
tile has reuse that pays for shared staging. For a reduction that consumes
each tile once, direct loads plus a fixed reduction tree may be the better
baseline. The tile element type and exact floating reduction contract are
missing from the fixture; preserve that as a contract question before claiming
determinism or numerical qualification. Do not use driver/channel/firmware
interfaces to emulate an unsupported instruction.
