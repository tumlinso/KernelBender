# Design briefs

## E01 — Compute only what the consumer observes

Let Q be the number of query batches in an epoch (1 or 32). The strongest conventional baseline is two FP32 GEMMs per query, X·A then (X·A)·B, followed by a rowwise sum of squares. The second GEMM can fuse the square/reduction only if the library or a custom epilogue supports it without harming the main product. This computes only the requested scalar and avoids storing any other result.

A materially different candidate is to form D=A·B once per epoch, then compute X·D and its row norm for each query. Ignoring the norm, its dominant multiply work is KMP + Q·BKP, versus Q·(BKM + BMP) for the chain; D costs KP FP32 storage. Replacing A or B invalidates D, so include its rebuild in every epoch, including Q=1. If parameters change after every batch, the rebuild is paid every batch and the chain is the safer baseline unless the actual dimensions still favor D. Dimensions are absent, so no universal winner follows.

The D path changes FP32 association and rounding. Compare both routes to an independent direct-FP32 oracle on representative random inputs and cancellation-heavy cases, checking the stated absolute and relative tolerance, especially outputs near zero. If X·A must be rounded to FP32 before B, that boundary is semantic: retain the first product and its FP32 intermediate; D cannot reproduce it in general. The atlas small tensor-circuit routes are unmeasured and need shape/precision justification; they are not an assumed shortcut here (R15 numerical contract; M24/C13).

## E02 — Preserve every position through a local state transition

Use the byte-per-site ping-pong kernel as the conventional baseline: each step reads old state and mask, obtains the periodic left neighbor, writes every new state, and the final step also contributes to an integer count of state 3. This is simple and robust for all N and T, but costs T launches and repeated state traffic. For N=31 or 33, a single CTA can keep the whole short ring local across T steps and unpack once; for N=1024 this may be plausible but should be compared with the ordinary grid; for N=65537 a single CTA is unsuitable.

A different representation packs 32 sites into each word using two state bit planes and a mask plane. Generate the rule as a Boolean network or a small runtime lookup, then evolve a tile with a T-site left halo and keep the evolving planes in registers/shared memory. Each CTA recomputes its halo and writes only its core, avoiding inter-CTA synchronization between steps. Handle ceil(N/32) words, mask invalid tail bits, and explicitly source site N−1 for site zero; N=65537 has a partial final word, so word-level wrap alone is wrong. Unpack the final state bytes and reduce per-CTA counts. Include packing, halo work, unpacking, and reduction; bit packing may repay these costs only for larger N or repeated steps.

The rule and mask are epoch-stable, but M01 warns that a runtime-varying truth table is not one immediate LOP3 instruction. Specialize a tiny circuit or use a correct table lookup; C06 is an example FSM composition, not evidence for this particular rule. If each intermediate state must be returned, materialize it per step and pay conversions/stores; if masks change every step, reread or repack each step and account for that traffic. Validate all 32 rule entries, every N/T combination, wraparound, tail masking, and the final count against a scalar oracle. The atlas mechanisms are hypotheses, not measured speedups.

## E03 — Reuse a packed parameter without assuming it is immutable forever

For one pair of queries, a direct fused GEMM path can read signed nibbles, sign-extend q, select the row’s scale for the 32-wide M block, form the represented FP32 weight, then accumulate in FP32. Reuse each decoded weight across the eight query rows within a tile. The two consumers use the same logical K×M weights: X·W and V·Wᵀ. This avoids a separate preparation launch and is the sensible one-pair baseline, subject to the quality of the tiled decode.

The shared-preparation candidate decodes the 8192 weights once per epoch into an immutable row-major FP32 K×M buffer (32 KiB), then runs both FP32 products for every query pair. Both consumers own read access to that buffer; the second uses the GEMM transpose mode. Do not duplicate a Wᵀ buffer unless measurement shows the library access pattern warrants another 32 KiB plus its transpose work. Include decode/store, both products per pair, packed/scale input updates, and any transfer cost. At Q=64 preparation is amortized across 128 consumer calls; at Q=1 it may lose to direct decode. Measure the crossover rather than infer it from the maximum reuse case.

The owner should version prepared weights by epoch: finish preparation, publish the immutable buffer with a stream/event dependency, and let concurrent consumers read it. An update creates a new version and invalidates the old one only after prior readers finish; it must not mutate storage under active consumers. Weight formation must round float(q)·scale to FP32 before accumulation, matching the represented-weight contract. Check both outputs against direct FP32 accumulation, including scale-group boundaries and tolerance edge cases. M18/C16 support treating layout as a producer/consumer map to test, while M08 cautions that packed integer dots have signedness/range contracts and do not replace FP32 accumulation of scaled weights. No timing or target GPU is supplied, so preparation wins remain unproven.
