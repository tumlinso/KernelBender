# E04 — Transfer the tiled copy intent to Volta

The intent that transfers is regular tile movement into shared memory followed by consumption under a producer/consumer ordering contract. The Hopper mechanism does not transfer: V100 is sm_70, which has neither TMA nor cp.async. A feasible public path is cooperative global loads through registers followed by shared-memory stores, a CTA barrier before consumers read the tile, and a second barrier before a reused buffer is overwritten. Double buffering may organize the stages, but it does not create an asynchronous copy engine; only claim overlap if the schedule and measurements establish it. This follows the Volta constraints in /sources/cuda/references/architectures/volta/programming-guide.md. The Atlas index routes synchronization questions to R06; its participation, visibility, and progress rules apply to any replacement barrier.

Before implementation, verify with the CUDA 12.9 programming/API and PTX documentation that the selected compiler emits a legal sm_70 image, which APIs are public and architecture-gated, and that no generated path silently requires a newer device. Check the documented arrival and visibility contract for the chosen CTA synchronization, including that every required participant reaches it. Establish the source and consumer ownership, tile bounds, strides, alignment, and any TMA zero-fill/swizzle behavior that must be reproduced. A plain copy preserves element bits; masked edge handling must reproduce the original values, and the consumer arithmetic must retain its stated order and FP behavior. Hardware limits include shared-memory capacity and the occupancy cost of staging (V100 has 96 KB per SM; allocations above 48 KB per block require opt-in). No Volta TMA equivalent should be assumed. Refs: /sources/cuda/references/architectures/volta/programming-guide.md, /sources/atlas/reference/R06.md, /sources/atlas/sources/S03.md.

# E05 — Turn the fixture into a causal experiment

Observed in this constructed fixture: B is 18% slower in ordinary end-to-end timing; one profiler replay reports 31% fewer global bytes, 1.7x issued instructions, and 2x registers per thread. B also contains a dependent consumer and irregular branch. These observations do not establish why it is slower. Conversion/issue cost, register-limited residency, branch effects, and too little independent work in the dependency chain remain hypotheses. Replay duration is not throughput evidence; there is no counter-to-source attribution.

First establish that the current A and B are semantically correct and race-free under a sanitizer on the same representative inputs. The earlier A race makes the comparison unsafe until current A is checked: if it persists, repair it or compare B with a safe independent reference, since a racy incumbent is not a valid performance baseline. Then use paired unprofiled runs in the same harness for the speed comparison, and a valid Nsight Compute capture only to explain the hot kernel.

Keep the diagnosis narrow: attribute conversion instructions and register use to source, then compare a B diagnostic that hoists/materializes a conversion outside the timed consumer while preserving its dependency and branch, against one that interleaves independent equivalent work while preserving the conversion path. Check outputs in both. More eligible warps and fewer dependency-stall cycles with the latter support insufficient useful parallelism; lower issue/register pressure and improvement from conversion hoisting support conversion/issue cost. If neither pattern appears, retain the uncertainty rather than tuning by guess. This uses the counter-versus-throughput boundary in /sources/cuda/references/profiling/hot-kernel.md and the bounded ILP comparison in /sources/atlas/mechanisms/M16.md.

# E06 — Keep SGEMM as the normal route

Use the verified cuBLAS SGEMM with FP32 inputs/accumulation and alpha=0.75, beta=0.25 so C is updated once as specified. Adapt the row-major buffers through the established cuBLAS call convention (or an already verified row-major wrapper), and verify dimensions, leading dimensions, and operand order; a transpose mistake can pass shape checks while computing the wrong product. Compare all outputs against the independent FP64 reference using the stated atol/rtol. The finite-input, dense, every-output contract fits a conventional GEMM, and the available verified implementation is the strongest baseline. The V100 programming guide explicitly routes dense math to cuBLAS.

An explicit request to reconsider formulation would justify one structural question: across the surrounding workload, are A or B reused, or can this GEMM be fused with adjacent work so that packing/precomputation or an owned epilogue amortizes its cost and removes extra memory traffic? The supplied contract establishes no such opportunity, so it does not justify a custom kernel by itself.

Choosing cuBLAS avoids designing and validating tile sizes, warp ownership, shared-memory staging and barriers, tail handling, register/occupancy tradeoffs, numerical accumulation behavior, launch geometry, and profiler-driven tuning. It also avoids maintaining a custom row-major mapping and proving every output path. References: /sources/cuda/references/architectures/volta/programming-guide.md, /sources/cuda/references/common/machine-aligned-design.md.
