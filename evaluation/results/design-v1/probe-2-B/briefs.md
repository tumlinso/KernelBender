# E04 — Transfer an algorithm across an architecture boundary

**Decision: conventional.** The intent that transfers is to stage each regular tile once and let its consumers reuse it while producer and consumer work are coordinated. The Hopper implementation mechanism does not transfer: V100 `sm_70` has neither TMA nor `cp.async`, and CUDA 12.9 does not make Hopper transaction barriers or headers a Volta contract. The feasible public path is coalesced global loads into registers, stores into shared memory, then a CTA barrier before consumers read the tile. Double buffering may retain overlap between independent tiles, but movement itself is synchronous and must be scheduled by SM threads. If shared reuse is absent, direct coalesced loads are simpler.

A CTA barrier preserves the handoff only if all required writers have completed, every required consumer waits, and participating threads can reach the barrier consistently. Prove the original barrier arrival/transaction rules and logical participant set; if correctness depends on an asynchronous completion count or a subset that cannot be mapped onto a convergent CTA barrier, the missing contract is that exact participant/visibility relation. Do not substitute the Atlas restricted copy-engine remapping lead: M37/R09 explicitly do not establish a public CUDA remap API. If staging copies bytes without changing the operator arithmetic, values can remain bit-exact; verify dtype, alignment, tail handling, and that arithmetic order/instructions are unchanged.

Before implementation, verify CUDA 12.9 documented `sm_70` API and instruction eligibility, compile explicitly for `sm_70`, and confirm generated target contains no Hopper-only path. Validate all tile edges against the independent operator reference and use a race/synchronization checker. # E05 — Separate an observation from its causal explanation

The fixture states that B is 18% slower in ordinary end-to-end timing; one profiler replay reports 31% fewer global bytes, 1.7x issued instructions, and 2x registers per thread. It also states a dependent consumer and irregular branch. These are fixture observations, not hardware results. They support competing hypotheses: B reduces traffic but exposes a dependency/branch path with little eligible work, or its representation adds conversion and issue cost and possibly register-limited residency. Register count and fewer global bytes alone establish neither cause. The old A race makes its historical result inadmissible. The current A is not yet known race-free, so first validate current A and B on the same cases, then run the required race/synchronization checks. Compare fresh versions only after both meet the same operator and numerical contract.

Next, make paired unprofiled measurements of the complete caller-visible work, with one fixed input set, warmup, repetitions, and timing boundary. Profile only the identified hot launch with line information and valid NCU counters; use source counters to connect stalls/instructions to code. Compare active and eligible warps/issue, dependency and branch behavior, instruction mix, registers/occupancy limits, and local-memory spill traffic. Low eligible work plus dependency stalls mapped to the consumer supports exposed dependency/parallelism as the cause. Extra conversion instructions or spills mapped to the conversion path, with corresponding issue/occupancy loss, supports conversion/issue cost. If the report cannot map those effects, label them unresolved rather than infer causality from replay time. Then run one narrow matched control that removes only the implicated cost while holding required work and inputs fixed; include any preprocessing in the full-path timing. NCU replay duration is diagnostic, never the throughput delta. Sources: `/sources/ncu-report-skill/SKILL.md`, `/sources/ncu-report-skill/reference/10-volta.md` (if target is SM70; its PM timeline is unavailable), `/sources/cuda/references/profiling/{hot-kernel,diagnostics-workflow}.md`, `/sources/kda/docs/experiment-engine.md`, `/sources/atlas/reference/R11.md`, `/kernelbender/references/experiments.md`.

# E06 — Keep the strong conventional route when it fits

**Recommendation for a normal implementation request: use the already verified cuBLAS SGEMM path.** Compute `alpha=0.75`, `beta=0.25` with the supplied row-major storage handled by its verified wrapper (or the equivalent cuBLAS column-major operand reversal), treating the incoming C as an input and output. This is dense, regular FP32 GEMM, every output is required, and ordinary FP32 accumulation is allowed. Preserve the full shapes and compare every result against the independent FP64 reference at `atol=2e-5, rtol=2e-5`; library accumulation order need not be bitwise identical. At about 100.7 million multiply-adds, cuBLAS owns mature tiling, coalescing, edge handling, register/shared-memory scheduling, and numerical implementation. The conventional choice avoids writing and debugging a GEMM schedule, shape/tail cases, accumulation path, and a custom benchmark/correctness implementation without a structural advantage to pay for it. Do not invent Tensor Core reduced-precision use, sparsity, or input reuse.

An explicit formulation-reconsideration request would justify one caller-boundary question: can a required adjacent producer or consumer be composed with this GEMM while still producing every required C value, so an extra full-tensor read/write or launch is removed? If not, keep SGEMM. Sources: `/sources/cuda/references/common/compute-libraries.md`, `/sources/cuda/references/common/machine-aligned-design.md`, `/sources/cuda/SKILL.md`, `/kernelbender/SKILL.md`.
