# Knowledge substrate and maintenance

## A bridge is not another hardware encyclopedia

A bridge links a recognizable problem structure to one or more computational mechanisms. Its content is: when to consider it; the semantic transformation; a minimal concrete construction; compatible hardware/source conditions; its possible economic gain; the costs that can defeat it; and the discriminating experiment. The native instruction specification remains in the primary source or KernelWiki.

Bridges are authored Markdown. A need map and direct links from SKILL.md are enough for the initial corpus. No embedding service, automatic card generator or graph database is required. Ordinary text/semantic searches in the installed environment may find relevant source material; direct reads verify it. During this design investigation, CUDA and Atlas were accessed by exact-path Project Control read calls, not agentic skill/investigator tools.

## Retrieval should expand and then ground the design

The agent starts from semantic relations: per-position multiplicity, local neighborhood routing, immutable linear composition, associative state, repeated decoding, or producer/consumer permutation. This can retrieve more useful material than only the familiar kernel name.

For executable advice, apply the exact architecture filter and inspect source/target notes. For analogy, a different-architecture example is allowed, but mark the mapping as an analogy and identify the mechanism that must change. If exact filtering yields nothing, broaden concepts—not the claim of compatibility. Missing evidence is a gap, not proof of hardware impossibility.

Usually load the main skill, the relevant caller/architecture references and a few cards. Context budgets are usability targets, not a rule to truncate a required numerical or participation condition. The source document is read when its exact contract could change the decision. Avoid loading the whole Atlas and all four GPU guides by default.

## Initial architecture coverage

The general method is independent of the generation. Volta has the deepest evidence substrate and receives concrete explicit-MMA, Boolean, ownership and lifetime examples. Ampere/Hopper/Blackwell contrasts teach the agent to reconsider whether the same transformation should be implemented through software staging, an asynchronous copy mechanism, a different collective scope or a different accumulator store.

Do not create a GPU backend/plugin framework. A short generation contrast and primary-source routes suffice. New devices require exact target/toolchain qualification, not another copy of the reasoning method. Hardware support is not monotone over marketing names, and a software intrinsic may lower differently from a native operation. [CUDA-AMPERE, CUDA-HOPPER, CUDA-BLACKWELL, PTX, AMPERE, HOPPER, BLACKWELL]

## Evidence axes that must survive

1. **Meaning:** operator identity, constraints and the allowed numerical interpretation.
2. **Support:** documented contract, implementation observation, dated measurement, reasoned hypothesis or unknown.
3. **Reachability:** public API, permitted PTX, binary analysis, restricted driver/firmware path.
4. **Applicability:** exact target, toolchain, shapes/representation/lifetime, source and binary.
5. **Outcome:** correct but slow, qualified gain, inconclusive, rejected semantics or not run.

These distinctions can be short labels/prose; they do not require a new schema covering all GPU facts. A theory-backed construction can be unmeasured. A measured speedup can have an uncertain causal explanation. A source-described feature can be unreachable through the permitted interface. Never collapse them into one confidence score.

## Keep learning external and reviewable

The agent can propose a small lesson after an experiment: the transferred mechanism, conditions, decisive counterexample or observed change, what remains uncertain, and links to exact evidence. A maintainer decides whether it belongs in KernelWiki, a bridge example or the continuing Atlas. Do not write to all three automatically.

Negative evidence should narrow a condition, not erase a design family. The existing W4A16 direct SIMT result constrains that code and contract, not every fragment-native decoder. The attention merge result supports a combined redesign, not a universal register-count threshold. A corrected binary does not inherit historical timing from its predecessor. [KW-LOWBIT, KDA-ATTRIBUTION, KW-ROUTE]

## Content ownership and portability

Drafts here are new syntheses with source locators; they do not vendor the CUDA/Atlas corpus or third-party implementations. Preserve attribution and check source licenses before copying code or extended text. The short KDA worked case remains a local-source example with its scoped provenance; publication does not silently upload private raw profiling archives.

The skill must remain useful when Project Control is unavailable: its own bridges are readable, and external locators state the workspace/path or official document needed. Local aliases can resolve dependencies in the host configuration; do not bake `/home/tumlinson` or historical GPU ordinals into runtime instructions. If a required source is absent, downgrade the claim or specify the missing check rather than inventing content.

Replace old source locators only through reviewed updates. There is no live knowledge ingestion background process. The implementation should retain the small component boundary so future replacements for CUDA or the Atlas can be substituted as evidence providers without changing the method.
