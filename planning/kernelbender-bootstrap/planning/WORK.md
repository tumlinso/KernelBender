# Implementation work: seven component outcomes

The design and initial skill material are already supplied. Implementation should refine/adopt them, not repeat the source investigation or build new orchestration. The native JSON persists input references and acceptance requirements in `notes`; arbitrary extra fields are not relied on.

## Order

`KB-01 → KB-02 → KB-03`; `KB-01 → KB-04`; `KB-02/03/04 → KB-05 → KB-06 → KB-07 → aggregate close`. One initial exclusive lane keeps integration simple. Existing bounded delegation can be used by the implementing agent without introducing a new system.

## KB-01 — Author the selective design skill and caller handoff

Dependencies: none.

Inputs: `DESIGN.md`, `design/CALLER_INTEGRATION.md`, `draft/skills/kernelbender/SKILL.md`.

- Adopt/refine the drafted entry, caller questions, need map and brief; preserve the existing repository/Task authority instructions.
- The same agent remains in control: no new agent invocation, hidden optimization loop, mandatory brainstorming quota or compulsory profiling of nonexistent kernels.
- The brief provides an actual construction and decisive next action; conventional routing and consequential unknowns are handled explicitly.
- The role is a design intervention, not a replacement for the continuing CUDA skill or Atlas.

## KB-02 — Adopt mechanism bridges with scoped architecture and source evidence

Dependencies: KB-01.

Inputs: `design/KNOWLEDGE.md`, `sources/ADJUDICATIONS.md`, `draft/skills/kernelbender/references`.

- Adopt ten compact problem-to-mechanism bridges and four worked examples, adding only material needed to make them accurate/useful.
- Each bridge has semantic construction, source/target/access limits, lifetime costs and a real falsifier; claims are not silently promoted.
- Volta-specific forms remain scoped; newer-generation contrasts are documented, not claimed locally qualified.
- The existing CUDA/Atlas content is referenced and selectively synthesized, not bulk copied, replaced or edited; attribution/licensing and private-source boundaries remain explicit.

## KB-03 — Validate the portable package and task-local KDA consumer

Dependencies: KB-01, KB-02.

Inputs: `design/CALLER_INTEGRATION.md`, `integration/KDA-INSERTION.md`, `draft/skills/kernelbender/assets/design-brief.md`.

- Add a small CPU content/link/frontmatter test suite and check clean installation of only skills/kernelbender; do not install evaluation answers.
- Demonstrate a task-local prompt/read/brief handoff using existing KDA documents/CLI conventions; register only actual source and do not invent engine fields.
- Explicit invocation works; activation descriptions distinguish special design from routine CUDA/profiling. Record host-specific registration actually used.
- No KDA source changes here: produce the narrowly scoped integration proposal for the separate KDA task.

## KB-04 — Prepare independent evaluation tasks and correctness boundaries

Dependencies: KB-01.

Inputs: `design/EVALUATION.md`, `evaluation/scenarios.json`, `evaluation/native-pilot.json`.

- Turn the supplied specifications into six small design probes and two specialized native task families plus a conventional control using the existing KDA task/evaluator contract.
- Create independent references, corrected valid baselines and withheld inputs; verify the exact Boolean rules, numerical semantics, preparation/update costs and boundary cases.
- Keep reviewer hints, holdout results and other-arm transcripts out of candidate-visible context. Do not make privacy depend on a directory name.
- Freeze workload and acceptance semantics before comparing agents; choose actual host/model/GPU budgets before execution, not after results.

## KB-05 — Test design behavior against the existing competent workflow

Dependencies: KB-02, KB-03, KB-04.

Inputs: `design/EVALUATION.md`, `design/RESEARCH.md`, `evaluation/scenarios.json`.

- Run bounded fresh-context A/B design probes with the same model/settings, source/tool access and effort budget. A includes current CUDA machine-aligned guidance and Atlas access.
- Review concrete constructions, semantic limits, context overhead, unlike families and decisive experiments; do not substitute a model novelty score for evidence.
- Correct consequential failures and use at most a small declared revision pass before freezing the native-pilot version. Preserve failed/negative outcomes.
- Record measured activation/behavior versus untested claims. A completed but unhelpful intervention is evaluated_not_promoted, not an invented success.

## KB-06 — Run the bounded paired native pilot and assess incremental value

Dependencies: KB-05.

Inputs: `design/EVALUATION.md`, `evaluation/native-pilot.json`, `design/CALLER_INTEGRATION.md`.

- Use existing KDA evaluation and CUDA controller/ported NCU skill, not a new optimizer or profiling framework. Bind actual GPU execution gates through the installed authority before running.
- Start one A/B pair per family and independently repeat any claimed skill-level win or unstable result, within the declared initial cap. Count all attempts and search costs.
- Validate generated kernels independently and compare complete caller-visible costs including preparation/update/extraction. Timing repetitions are not independent agent trials.
- Report individual kernel promotion separately from skill-level evidence. A negative or inconclusive pilot is a legitimate result and must not expand into an unbounded benchmark epic.
- Only if useful, run a material-only ablation on one informative case; do not automatically triple the full study.

## KB-07 — Finalize the component and issue a versioned KDA handoff

Dependencies: KB-03, KB-06.

Inputs: `DESIGN.md`, `design/EVALUATION.md`, `integration/KDA-INSERTION.md`, `planning/INTAKE.md`.

- Choose full adoption, narrower activation, substrate-only simplification or experimental status from the actual results; do not claim general creativity gains from package checks.
- Run compact package/regression checks and preserve evidence/source identities. The shipped skill excludes evaluator answer notes and raw private archives.
- Supply the tested KernelBender commit, actual skill path, evidence-qualified status and minimal KDA changes for the separate integration authority.
- Keep unresolved performance opportunities small and concrete; no CUDA/Atlas replacement, additional agent system or all-architecture framework is added.

## Separate KDA integration

`planning/kda-integration.todo-plan.json` contains one task for the `kda` workspace. It has no fabricated cross-project task dependency: verify the component handoff at intake. It must not be applied before an accepted commit and adoption decision exist. Keep the nested skill path explicit and the evaluator untouched.

No implementation plan in this package retires the CUDA skill or Circuit-Bending Atlas. The evaluation may recommend retaining only a simpler intervention; that is evidence-driven completion, not a reason to invent more work.
