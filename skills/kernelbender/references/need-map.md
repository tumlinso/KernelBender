# Enter through the computation

This table routes to the ten compact bridges. For the wider mechanism and construction library, follow [problem-first opportunities](opportunity-index.md); open only the card needed for the present choice.

| Structural clue | Start with | Then test the limiting boundary |
|---|---|---|
| The next stage uses only a small statistic of a large intermediate | `bridges/demand.md` | Intermediate rounding, nonlinearities and external observability |
| Parameters/support are reused through many calls | `bridges/lifetime.md` | Update horizon, maintenance, capacity, preparation timing |
| A producer stores a layout the next kernel immediately repacks | `bridges/ownership.md` | True lane/slot maps, live state and synchronization |
| Many independent small discrete rules or per-position counts | `bridges/bitplanes.md` | Encode/decode frequency, mask boundaries, output semantics |
| Local topology/categories are stable and indexing dominates | `bridges/identity.md` | Reordering/deletions, external ID recovery, neighbor dependencies |
| An unusual bounded dot, bilinear map, min-plus or lookup operation | `bridges/arithmetic.md` | Native exact form, range and lost information |
| Sequential code has a composable state or sufficient statistic | `bridges/summaries.md` | Summary size, associativity, finite-precision and input availability |
| Low useful parallelism or too much live state in one fused region | `bridges/parallelism.md` | Partial-state merge, recomputation, extra traffic and scheduling |
| Most decisions are far from a threshold | `bridges/refinement.md` | A justified error bound, ambiguity rate and fallback cost |
| Communication/format work exceeds the useful computation | `bridges/boundaries.md` | Public interface, ownership, response/setup and coherence |

Look for a structural analogy outside the original kernel family when local recipes keep repeating. Explain the correspondence explicitly: source operation → representation → target operation. A shared name or visual resemblance is not an analogy with computational content.

Use KernelWiki's exact-target route for implementation facts, and a broader conceptual search for transferable ideas. Treat older/different-generation results as examples to reinterpret, not as eligibility. Follow only the source that could change the current decision. Read correctness prerequisites even when they are not the exciting part of the design.

A missing row here is not a stop condition. Derive another representation from the task's algebra/information flow and ground the required mechanism. Conversely, selecting a row does not require implementing its exotic candidate.
